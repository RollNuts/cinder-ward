# Issue #5 Vertical Slice Pipeline

対象: 1週間で「主人公1体 + 暗い1部屋 + 巨大敵気配 + Idle/Move/Attack/Hurt + PCビルド」を作るための具体手順

## 1) エンジン選定の現在判断

方針としては「**Godot 4.7 を最優先実装**」とし、1週間で実験結果が確認できる状態では
**Unity/Unreal は比較対象**として扱う。  
最終確定は「1週間縦断スライスが成立するか」を見て判断する。

- 現在判断: **現時点では Godot 4.7 first**
- 判定基準（いずれか 1 つでも不成立なら比較エンジンへ切り替え検討）
  - 1日に1回のビルド更新で、1部屋・4ステート動作・PCビルドが回ること
  - 2人称(固定中距離/俯瞰寄り)パースを確立できること
  - 60秒以上連続プレイできること（クラッシュなし）
  - 既存の無料素材ルールを守って、最終素材に乗せるまでの流れを確認できること
  - PC向けエクスポートが週内で1回以上成立すること

比較条件:
- Unity: 2D編集体験、Inputの安定性、Steamビルドの社内ノウハウ差分を確認
- Unreal: 3Dの見栄え品質と2.5Dの見た目合わせ速度を確認
- Godot: 上記5項目の速度・再現性・導線の簡潔さを比較

## 2) Godotでの最初の実装手順（最短ルート）

### 2.1 Day 1-2: 土台を先に立てる

1. Godot 4.7 プロジェクトを新規作成（2D）し、必要最小のシーンを作る  
   - `Main` シーン: ゲーム起点
   - `Room` シーン: 暗い1部屋（床/壁/小道具）
   - `Player` シーン: 4ステート（Idle/Move/Attack/Hurt）
   - `ThreatProbe` シーン: 巨大敵気配表現（画角揺れ・音・ライト色）
2. 入力マップを1セットに集約  
   - `move_left`, `move_right`, `move_up`, `move_down`, `attack`
   - エディタ上でキー再割り当て可能な状態にしておく
3. キャラの最低動作を実装  
   - Idle/Move は移動状態遷移と簡易アニメ制御
   - Attack は1ヒット判定のクールダウン付き
   - Hurt は被弾演出1種（色変化/ノイズ/ノックバック）
4. カメラ/雰囲気を整える  
   - 暗めトーン、コントラスト、局所スポットライト風の環境で
   - 3D素材の元ポーズが取り込める基準レイヤーを先に決める

### 2.2 Day 3-4: 縦断データフローを1周

1. Maya/Blenderで作ったラフモデル/ポーズをレンダープレビュー
2. PixelOverへ下描きをインポートしてポーズ/シルエット確認
3. AsepriteでPixelOver版を清書（1体分）
4. Godotへ差し替え、1部屋に配置して見え方を微調整
5. 敵気配（巨大敵）を導入  
   - 直視できない代わりに、間接表現（遠方点滅、床の歪み、音）で恐怖演出
6. PCビルド（最低1回）  
   - `--export` で最小実行可能ビルドを作成

### 2.3 Day 5-7: 仕上げるべき最小到達条件

1. 攻撃→被弾→回復（最小）までの最短ループを成立
2. 画面全体の可読性確認（背景黒つぶれ防止、敵気配の見える層を確保）
3. 1週間版のスモークテストを完了
   - 起動 → 60秒動作 → 攻撃1回 → 被弾1回 → ビルド再起動

## 3) Maya/Blender/PixelOver/Aseprite の実作業フロー

- 目的は最終2Dアセット制作。3Dは**構図・ポーズ・陰影の下地**に限定。
- 最終アートは必ず Aseprite で手仕上げし、最終コミット前に3Dレンダから分離。

### 3.1 Maya

- ラフポーズの作成、主に体幹と腕の動線・間合い把握
- 表情とシルエットは簡素化して作業時間を抑える
- 出典のライセンス不明素材は本番では使用しない
- 目的ファイルを `wip` タグとして扱い、最終納品に直接使わない

### 3.2 Blender

- 部屋のスケール検証、床/壁の遠近スナップ検証
- カメラ角度と敵気配の空間的圧迫感を決める
- 背景レンダは高解像度オフスクリーンで撮って、PixelOverに入れる

### 3.3 PixelOver

- 3D下描きから主要ラインを作る
- 2.5D中間層を先に作ってからAseprite清書に渡す
- 影の方向と輪郭の太さを部屋単位で統一

### 3.4 Aseprite

- Idle/Move/Attack/Hurt をピクセル単位で完成
- 色数を制限（ダーク系限定）し、画面に滲む明るさを抑える
- 攻撃モーション差分を1～2コマで成立させ、見える情報を優先

## 4) 無料素材の商用安全ルール

### 4.1 ルール原則

1. ライセンス文書が**明示的に商用可**でない限り、本番素材として採用しない
2. 再配布可否（配布用データとしての利用制限）を必ず確認
3. 2次改変可否を確認し、必要なら attribution（クレジット）を記録
4. 未確認素材は一時保管のみ、商用公開対象外

### 4.2 既定許可ソース

- Poly Haven: CC0 前提、明記内容を添付保存
- Mixamo: 商用利用可の運用可否を確認済み前提で使う
- Unity/Unreal向けの商用素材パック使用時も同様にライセンス保管

### 4.3 要確認素材

- Fab / Sketchfab: ライセンスURLを毎回保存し、以下を確認
  - 商用利用可
  - 再配布条件
  - 改変可否
  - ゲーム内利用時のクレジット要件

### 4.4 禁止ライン

- Maya付属素材で商用ライセンスが不明の場合、縦断スライス本体に載せない
- 参照元不明画像/動画素材の採用
- 使用条件に「非商用」「作品内限定」等の制限がある素材

## 5) 生成物保存ルール

- 命名規則（原則）  
  `YYYYMMDD_<source>_<category>_<ver>.<ext>`  
  例: `20260629_blender_room_blockout_v01.blend`
- ロケーション
  - `assets/source/` : 元データ（.blend/.ma/.fbx）
  - `assets/reference/` : PixelOver/Aseprite下描き用参照
  - `assets/final/` : ゲーム投入版
  - `docs/asset-licenses/` : 取得したライセンス証跡の保存先
- 判定状態
  - `wip`: 試作段階。最終ビルドへ自動参照しない
  - `ready`: Aseprite最終化し、縦断スライス本体に含める可
  - `reject`: 仕様違反/ライセンス不整合/品質不備
- 追跡情報として毎件
  - 取得元URL
  - ライセンス文面（要約）
  - 参照日
  - 最終用途
- 破棄規則
  - `reject` は削除不可。再利用可否を明示したうえで保管継続

## 6) 1週間スプリント

### Day 1（M1）

- Godotの空プロジェクト、基本シーン構成、入力マップ、最低動作を整備
- Maya/Blenderで部屋ブロックアウト候補と主人公ラフポーズを作成開始

### Day 2（T2）

- 3ステート（Idle/Move/Attack）を実装
- Hurtは未確定でも被弾演出の仮配置
- 低解像度背景で明るさ/コントラストを先決

### Day 3（W3）

- プレイヤー4ステートをすべて通るようにする
- 威圧的な巨大敵気配（見えすぎない演出）を実装
- Blender/MayaレンダをPixelOverに取り込む

### Day 4（Th4）

- Aseprite清書開始、背景/敵気配の可読性を固定
- Godot反映を複数回し、見え方を最終化
- ライセンスチェックの一次締切

### Day 5（F5）

- PC向けビルドを作成し、再現手順を記録
- 60秒プレイ＋攻撃1回＋被弾1回の通過テスト
- 問題箇所をIssue 1本で洗い出し

### Day 6（Sa6）

- 画質/挙動を1回修正し、Aseprite最終差分を反映
- 動作が破綻しないよう最小最適化
- スプライト差分を最終版に固定

### Day 7（Su7）

- スモークテストを最終実行
  - 起動→入力→攻撃→被弾→再起動→ビルド再作成
- 1週間評価会議に向けて成果物一覧とリスクを確定
- 判定: 継続（Godot） or 切り戻し

## 7) 切り戻し条件（比較対象切り替え）

- 7つの基準のうち2つ以上が Day4 の終わりまでに成立しない
- PCビルドが1回も成功しない、または再現性がない
- 1コア想定でフレームレートが不安定（体感的に著しく読みにくい）
- 3D下描きと2D清書の往復コストが高く、Aseprite反映が進まない
- 無料素材の商用安全確認が完了しない

上記の場合は、即日で比較対象（Unity、Unreal）へ同条件での再計測を開始し、  
次回評価までに「再生、編集導線、PCビルド可否」を再検証する。
